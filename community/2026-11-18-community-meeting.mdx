The November 18, 2026 wasmCloud community call was a KubeCon recap. Bailey Hayes argued that most of what was called an **AI agent sandbox** at the conference was not a sandbox. She then showed wasmCloud running more than a million Codex agents on one 64-core Arm server and 17 models at once on one NVIDIA L4 through WebGPU. The call closed with two RFCs, workload identity and credential brokering, and the threat model that will check them.

## Key Takeaways

- **A sandbox has to deny by default.** Bailey and Eric Gregory's KubeCon [sandboxing workshop](https://github.com/cosmonic-labs/sandbox-workshop-kcna26) runs [GTFOBins](https://gtfobins.github.io/) "evil" builds of common CLIs inside WebAssembly, and each tool gets its own sandbox. Using the NIST definition (isolation, least authority, deny by default), Bailey said a container or a microVM is not a sandbox on its own
- **1.42 million warm components on one Arm server.** On an EC2 `c9g.16xlarge` with 64 Arm Neoverse-V3 cores and 128 GB, the [`scale_density` benchmark](https://arewefastyet.wasmcloud.com/density.html) held 1.42M warm components at 82 KiB each, with a 1.4 ms request p99 at the top. It also held 9.65M scale-to-zero workloads and reached 179k cold starts per second
- **A million Codex agents, limited by etcd and disk.** Codex compiled to Wasm, running in one pod on one Arm worker, reached 1,002,000 hosted workloads, each answering a mock OpenAI endpoint. The limits were Kubernetes etcd and local SQLite session storage, not CPU or memory. The operator now schedules about 75,000 workloads per second
- **The Cosmonic Agent SDK is open source.** The [Agent SDK](https://github.com/cosmonic-labs/agent-sdk) launched at KubeCon. It turns the OpenAI REST API and session storage into WIT interfaces. Eric Gregory and Victor Adossi have Pi, Hermes, Goose, and Codex compiling to Wasm with it
- **17 models on one GPU, with about 4% Wasm overhead.** NVIDIA MIG splits a GPU into at most seven slices. With `wasi:webgpu`, Bailey and Mendy Berger served 17 models at once on one L4. In the [GPU benchmark](https://arewefastyet.wasmcloud.com/gpu.html) the Wasm sandbox cost about 4% against native WebGPU. WebGPU itself still trails CUDA: 32.1 tok/s against 53.6 tok/s for Qwen2.5 7B generation
- **Workload identity and credential brokering RFCs.** [Workload identity (#5653)](https://github.com/wasmCloud/wasmCloud/issues/5653) settles the SPIFFE ID for each workload. [Credential brokering (#6007)](https://github.com/wasmCloud/wasmCloud/issues/6007) builds on it: the host puts secrets into outgoing requests, so the guest never holds them. Bailey's draft PRs are open, and she plans a demo next week
- **A threat model that both people and LLMs can read.** The wasmCloud repo now has a [capability catalog](https://github.com/wasmCloud/wasmCloud/blob/main/docs/security/capability-catalog.yaml) and a [threat catalog](https://github.com/wasmCloud/wasmCloud/blob/main/docs/security/threat-catalog.yaml) that model threats such as confused deputy. Bailey runs an automated security audit against them before every release
- **wasmCloud 2.12.2 shipped plugin volume mounts.** The [2.12.2 release](https://github.com/wasmCloud/wasmCloud/releases/tag/v2.12.2) includes Aditya Salunkhe's [host component plugin volume mounts (#5673)](https://github.com/wasmCloud/wasmCloud/pull/5673), and Jeremy Fleitz has a PR open for [NATS bucket creation (#5981)](https://github.com/wasmCloud/wasmCloud/pull/5981)

## Meeting Notes

### The KubeCon Sandboxing Workshop

Bailey Hayes opened the first call after [KubeCon + CloudNativeCon NA 2026](/blog/wasmcloud-at-kubecon-cloudnativecon-na-2026/) with a recap. She and Eric Gregory ran a workshop, [sandbox-workshop-kcna26](https://github.com/cosmonic-labs/sandbox-workshop-kcna26) ([slides](https://docs.google.com/presentation/d/1FMS8lKRVUmiSbDSCtlBDMWiE0bQEnhnVCUfewjDY6_k/edit)), that builds an agent with WebAssembly from first principles, without the Cosmonic Agent SDK. Eric's idea was to use [GTFOBins](https://gtfobins.github.io/), a catalog of ways that common binaries can be abused. The workshop runs these "evil" binaries inside WebAssembly, where they stay sandboxed.

The workshop makes two points. First, WebAssembly is the strongest sandbox you can use. Second, sandbox the agent separately from its tools. Bailey gave an example: an agent that is asked to reach a user database but may only use `curl` can still open a SQLite connection if it can rewrite the binary. The agent isn't malicious, it is only trying to finish its task. So don't give it ambient authority over everything in a container. Sandbox each tool on its own. Jeremy Fleitz showed this later in the call from a GitHub Codespace: the agent, `curl`, and `sqlite` are separate components that call each other through WIT contracts, and an attempt to write `/etc/passwd` fails with a permission error. The workshop runs in Codespaces, so you don't need to install anything.

### What Counts as a Sandbox

Bailey said half of KubeCon was about sandboxing AI, and that the industry needs a definition. In her view a microVM is not a sandbox, and neither is a container. You can build a sandbox on top of them, but you don't start with one. The workshop slides, a collaboration between Eric and Liam Randall, use the NIST SP 800-95 definition: a sandbox gives **isolation**, **least authority**, and **deny by default**, so it can safely run untrusted code. Liam added that NIST is the baseline most Fortune 500 companies adopt, and that classified systems use an even stricter definition. Bailey called it table stakes, and said most of the projects she saw at KubeCon didn't meet it. Another slide, which Eric credited to Liam, explains capabilities with the permission prompts that phones and browsers already show.

The workshop also changed how the team describes wasmCloud. The old message was "write once, run anywhere," polyglot cloud-native development. The new one starts from the problem: you need a sandbox, and all code is untrusted. Bailey later listed what that covers: vibe-coded apps, MCP servers, agents, the tools agents call, and the REST endpoints they reach. For how wasmCloud enforces this on Kubernetes, see [workload security](/docs/kubernetes-operator/workload-security/) and [network access and socket isolation](/docs/wash/developer-guide/network-access-and-socket-isolation/).

### Density on Arm Neoverse

Arm gave the team access to an Arm Neoverse server. Until now, wasmCloud's density numbers came from developer MacBooks and a low-cost Hetzner Ryzen 5 runner, which is x86. This was the first run on the kind of server people use in production. Bailey said more than half of the new compute at hyperscalers is Arm. Liam noted that one on-prem data center company they met at KubeCon runs no Arm at all. Bailey first showed these numbers live on the [November 11 call from KubeCon](/community/2026-11-11-community-meeting/); for the x86 baseline, see the [176,000-per-host run from October 28](/community/2026-10-28-community-meeting/).

The [`scale_density` benchmark](https://arewefastyet.wasmcloud.com/density.html), which Victor Adossi first wrote (see the [November 4 call](/community/2026-11-04-community-meeting/)), ran a basic `wasi:http` handler on one `wash-runtime` process. The host was an EC2 `c9g.16xlarge` with 64 Arm Neoverse-V3 cores, 128 GB of memory, and two NUMA nodes:

| Metric | Result |
| --- | --- |
| Warm components | 1.42M |
| Scale-to-zero workloads | 9.65M |
| Memory per warm component | 82 KiB (host memory, page tables included) |
| Request p99 at the top | 1.4 ms across 1.42M warm components |
| Cold starts per second | 179k |

The limit was cores for concurrency, not memory. The benchmark measures how many sandboxes one host can run at once. For running that kind of density on Kubernetes, see [lightweight deployments](/docs/kubernetes-operator/operator-manual/lightweight-deployments/) and [autoscaling WorkloadDeployments](/docs/kubernetes-operator/operator-manual/autoscaling/).

### A Million Codex Agents on One Arm Worker

Agent Substrate, a newly announced project, showed about 22,000 idle agents across 65 microVM nodes. Bailey ran a comparison on the same Arm server, set up as a Kubernetes worker. One pod ran Codex, which Eric had compiled to WebAssembly. Each agent sent one query to a mock OpenAI endpoint that returned a valid OpenAI response, so the run didn't spend real tokens. The run passed **one million** hosted agents. A recorded Cosmonic Control dashboard showed 1,002,000 hosted workloads and a 39.02 GiB host pod working set, with 540,000 chats verified at that point. Requests per second were close to the basic HTTP component's.

CPU and memory were not the limits, and Bailey had about 20 GiB of memory left:

- **etcd** has serious scale issues at this size. Next time she would use Postgres, which is what Agent Substrate did.
- **SQLite session storage** writes each agent session to local disk so the agent can scale to zero and wake later. The server was in Arm's AWS account, so she couldn't attach a bigger EBS volume. Next time she might reconcile sessions to S3 and skip the local cache.

Making the video took operator work. Argo CD couldn't render a million custom resources, so Bailey built a Perses dashboard instead. A series of PRs from Bailey and Victor raised the operator's concurrency until it scheduled about **75,000 workloads per second**. For the resources involved, see the [runtime operator CRDs](/docs/kubernetes-operator/crds/). Bailey has published the benchmarks with their Ansible playbook, Terraform, and GitOps repo, because the numbers are hard to believe otherwise.

Frank Schaffa asked whether K3s would have avoided the etcd limit, since it can use another datastore. Bailey said yes, but she only got the Arm box on the Saturday before a Wednesday talk. He also asked how microVMs compare with Wasm sandboxes. Bailey called it apples and oranges. Agent Substrate runs its own Go agent, built on its own A2A-based SDK, inside gVisor, with a full operating system and its CLIs in the same sandbox, and relies on network policy. wasmCloud runs stock wasmCloud, where an agent is just a component that has an HTTP capability. wasmCloud also inherits the network controls of the cluster it runs in. Frank asked the team not to focus only on agents, because each sandbox can hold any function. Bailey agreed. Aditya Salunkhe asked whether the 22,000 were real agent loops. Bailey said they were plain calls to a small Go app, not an agent harness like Codex.

### The Cosmonic Agent SDK and Aditya's ARM64 Emulator

Cosmonic open sourced the [Agent SDK](https://github.com/cosmonic-labs/agent-sdk) at KubeCon. Bailey's summary: it is the OpenAI REST API turned into WIT. You can use OpenAI as the inference provider or plug in your own component. It also defines WIT for session storage, so sessions can be distributed and durable. Eric led most of the work, with Victor contributing. Bailey invited anyone in the industry, including Aditya, to help define the right capability contract for agents built with any framework, such as A2A, Codex, Claude, Goose, Pi, or Hermes.

Aditya said he now has a full ARM64 CPU emulated inside WebAssembly. With snapshotting, it boots in about 12 ms, and it isn't multi-CPU yet. This follows his RISC-V Linux sandbox from the [October 14 call](/community/2026-10-14-community-meeting/). Victor noted that with only cooperative threads, multi-core support won't add much speed but will let more run at once. Aditya said a spike gained about 10 to 20%.

### Why the Story Works Now

Liam compared this moment to rolling out containers and Kubernetes in 2014, when he had to walk Fortune 100 companies and US government teams through the paradigm shift. He thinks AI is forcing that shift faster this time. He said the scale result alone isn't what convinces people. It is the full chain: trust starts in Wasm, adds the component model and Wasmtime for each tenant, then wasmCloud's multi-tenancy and policy enforcement points, then Kubernetes integration. A year ago the Kubernetes piece wasn't there. Five months ago the policy enforcement points weren't. Two months ago the scale wasn't. Bailey has follow-up meetings with the Agent Substrate team.

### WebGPU: 17 Models on One NVIDIA L4

The other half of KubeCon, Bailey said, was about sharing scarce GPUs. Most approaches use NVIDIA's Multi-Instance GPU (MIG), which splits a GPU into at most seven slices. Bailey and Mendy Berger ([repo](https://github.com/cosmonic-labs/KubeCon-2026-NA-GPU), [slides](https://docs.google.com/presentation/d/1XSuhDqWWACD6UbhuxEaW_ebqrtHIU-ECw8BWaz27JJE/edit?usp=sharing)) used **WebGPU** instead. It is the web standard that browsers use to share GPUs across consumer hardware, and wasmCloud uses the same `wgpu` crate as Firefox. On one NVIDIA L4 they served **17 models at once**, including Qwen and Llama. Mendy demonstrated ONNX Runtime, TensorFlow.js, and llama.cpp compiled to Wasm, plus a Rust driver. Each was a component doing a different kind of work on the same GPU. The docs list a [WebGPU TensorFlow example](/docs/examples/#webgpu-tensorflow) you can run with `wash dev`.

The new [GPU benchmark](https://arewefastyet.wasmcloud.com/gpu.html) from [PR #5898](https://github.com/wasmCloud/wasmCloud/pull/5898) (not yet merged) separates the two costs. It ran Qwen2.5 7B Q4_K_M on an L4:

| Path | Prompt processing (pp512) | Generation (tg128) |
| --- | --- | --- |
| Vendor (CUDA) | 3,466 tok/s | 53.6 tok/s |
| WebGPU, native binary | 24.5 tok/s | 33.4 tok/s |
| WebGPU inside Wasm | 24.3 tok/s | 32.1 tok/s |

Wasm adds 0.7% to 4% over native WebGPU, which is the cost of the sandbox, multi-tenancy, and shipping the GPU kernel inside a component. The gap to CUDA is in WebGPU, and the page notes that llama.cpp's WebGPU backend may leave work on the CPU. Closing that gap upstream will matter most. The demos needed patches across the ecosystem that only exist on a branch for now, and Mendy has spent the past week upstreaming them. Bailey also cut about 30% off model load time in one day of work. One more advantage: when a MIG slice faults, the whole device faults, but in WebGPU a fault is a trap and the device keeps running. For enabling the interface, see the [host interface configuration reference](/docs/kubernetes-operator/host-interface-configuration/) and the [runtime feature list](/docs/runtime/).

### Workload Identity and Credential Brokering RFCs

[Workload identity built on mTLS (#5653)](https://github.com/wasmCloud/wasmCloud/issues/5653) was on the [Q4 roadmap](/community/2026-09-30-community-meeting/), and Bailey had proofs of concept in draft before KubeCon. The main design question was what the **SPIFFE ID** for a workload should be. She asked everyone to review it and plans a full demo once it lands, hopefully before next Wednesday.

[Credential and secret brokering (#6007)](https://github.com/wasmCloud/wasmCloud/issues/6007) is new. Bailey said it was the one thing other sandboxing projects at KubeCon did that wasmCloud didn't. It builds on workload identity. When a workload makes a `wasi:http` request that needs an API key, the guest doesn't hold the key. The host swaps a placeholder for the real secret on the way out. Bailey quoted a line from Liam: "you can't leak what you don't have." The same design covers any host plugin API, any secret, and real credentials, including token exchange and refresh for mutual TLS. A new WIT interface tells native and host component plugins when to broker an egress request. The draft PRs are [egress secret substitution (#5986)](https://github.com/wasmCloud/wasmCloud/pull/5986), [`wash dev` secrets (#5987)](https://github.com/wasmCloud/wasmCloud/pull/5987), and [`wasmcloud:broker` with token exchange and DPoP (#5990)](https://github.com/wasmCloud/wasmCloud/pull/5990). For today's model, see [secrets and configuration](/docs/kubernetes-operator/operator-manual/secrets-and-configuration/) and [bring your own TLS certificates](/docs/recipes/tls-bring-your-own-certificates/).

### The Confused Deputy and a Machine-Readable Threat Model

Frank asked what risk comes from letting plugins change requests in flight. Bailey said wasmCloud's threat model is a multi-tenant host. Many other projects, including Agent Substrate, give each tenant its own privileged container or microVM. wasmCloud's biggest risk is the **confused deputy**. If a plugin builds a table of workloads by identity when they bind, and an off-by-one bug mixes up the connection pools, one tenant could use another tenant's credentials.

To earn the OpenSSF badge (see the [November 4 call](/community/2026-11-04-community-meeting/)), the project completed an OpenSSF security self-assessment and went on to a Gemara-style assessment. The model started in fintech with FINOS, which modeled common cloud-native controls such as TLS and OCI. wasmCloud then modeled its own capabilities in a [capability catalog](https://github.com/wasmCloud/wasmCloud/blob/main/docs/security/capability-catalog.yaml): running untrusted code, pulling it from OCI, a NATS control plane, HTTP ingress, and volume mounts. Its threats go in a [threat catalog](https://github.com/wasmCloud/wasmCloud/blob/main/docs/security/threat-catalog.yaml), including confused deputy, elevation of privilege, and spoofing. Bailey said LLMs are much better at audits when they get the exact boundary and the threats that apply to it, not "find a bug in my code." She now runs an automated audit before every release, and plugin authors can use the same catalogs.

The project also replaced personal access tokens with short-lived, per-workflow tokens from [Octo STS](https://github.com/octo-sts). Its [security insights file](https://github.com/wasmCloud/wasmCloud/blob/main/security-insights.yml) lists the rest: baseline scan results uploaded for OpenSSF bots, OpenSSF Scorecard, DAST and SAST, fuzzers, OSV-Scanner, Dependabot, CI hardened with zizmor, and license scans. You can [verify wasmCloud releases and SBOMs](/docs/verify-releases/) yourself.

### Architectural Security

Liam added that cloud providers limit things like how fast certificates can be minted, and that at wasmCloud's scale those limits are easy to pass. Other platforms run into IP exhaustion and certificate limits at a fraction of this scale. Choosing the unit of tenancy carefully is what lets the design fit into GCP or AWS. Bailey called the alternative approach "whack-a-mole": proxies with hard-coded secret locations, and agents asked to "pretty please" use placeholders. That can't hold up with non-deterministic agents. Liam's name for the alternative is **architectural security**. You can put a non-deterministic advisor inside an architecture that enforces security, but you can't replace that architecture with an LLM. He and the team have drafted an academic white paper on the idea. Bailey asked everyone to help spread the word.

## WebAssembly News and Updates

In **webassembly news** this week, KubeCon NA 2026 split into two topics: sandboxing AI, and sharing scarce GPUs. WebAssembly speaks to both. On sandboxing, the [Component Model](https://component-model.bytecodealliance.org/) gives every tool and agent its own deny-by-default boundary, and the density numbers make a sandbox per tool affordable. On GPUs, [WebGPU](https://www.w3.org/TR/webgpu/) and the [`wgpu`](https://wgpu.rs/) crate bring the browser's multi-tenant GPU model to the server through `wasi:webgpu`. The gap to CUDA is now mostly in upstream WebGPU backends. Supply-chain security keeps maturing too, with the [OpenSSF](https://openssf.org/) self-assessment, Gemara-style threat models, and short-lived CI tokens.

## What is wasmCloud?

[wasmCloud](/) is a CNCF project for building applications out of [WebAssembly components](/docs/overview/workloads/components/) and running them across cloud, edge, and [Kubernetes](/docs/kubernetes-operator/) clusters. The [Wasm component model](/docs/overview/workloads/components/) lets you write business logic in Rust, Go, Python, TypeScript, C#, Java, and more. The platform supplies capabilities like HTTP, messaging, key-value storage, blob storage, secrets, GPU access, and observability through [standard interfaces](/docs/overview/interfaces/) and a pluggable [host plugin](/docs/overview/hosts/plugins/) architecture backed by [Wasmtime](https://wasmtime.dev/). [`wash`](/docs/wash/) is the developer shell for building, running, deploying, and debugging. The [runtime operator](/docs/kubernetes-operator/) schedules Wasm workloads on Kubernetes the same way you schedule containers, with [WASI Preview 3](/blog/wasi-p3-on-wasmcloud/) support on by default. Every workload starts with no capabilities and gets only what it is granted, which makes wasmCloud a deny-by-default sandbox for untrusted code, AI agents included.

## Topic Deep Dive: What Makes an AI Agent Sandbox

An **AI agent sandbox** has to do more than put an agent in a box. Bailey's KubeCon argument has two parts. First, the boundary must deny by default. A microVM or container starts with a whole operating system and all its binaries, and you have to remove what the agent shouldn't touch. A WebAssembly component starts with nothing and gets each capability it is granted, such as [`wasi:http` with an allow-list of hosts](/docs/wash/developer-guide/network-access-and-socket-isolation/). Second, the boundary belongs around each tool, not only around the agent. In the workshop, `curl` and `sqlite` are separate [components](/docs/overview/workloads/components/) that the agent calls through WIT. A rewritten binary can't reach a database it wasn't given, and writing `/etc/passwd` fails. For how wasmCloud isolates workloads that share a host on Kubernetes, see [workload security](/docs/kubernetes-operator/workload-security/) and the [zero trust security post](/blog/zero-trust-security/).

This model only works if it scales, and that is what the KubeCon numbers show. At 82 KiB per warm component, one Arm server holds 1.42 million sandboxes, and a million Codex agents ran in one Kubernetes pod. The limits were etcd and disk, not the runtime. That density makes one sandbox per tool affordable, and it is the setting the next two RFCs are designed for. [Workload identity](https://github.com/wasmCloud/wasmCloud/issues/5653) gives every sandbox a SPIFFE ID, and [credential brokering](https://github.com/wasmCloud/wasmCloud/issues/6007) keeps API keys out of guest memory. A multi-tenant host with brokered credentials has to guard against the confused deputy, which is why both RFCs update the threat catalog. To try the pattern yourself, start with the [quickstart](/docs/quickstart/), then [deploy a WebAssembly workload](/docs/quickstart/deploy-a-webassembly-workload/) to Kubernetes.
